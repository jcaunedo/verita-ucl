*The setup, in general*: The component library lives in its own repo, separate from the apps that use it. It holds our shared UI components plus one CSS file with the design tokens (colors, type, spacing). A bundler (e.g. tsup, Vite or Rollup) compiles it into a package with three parts: the compiled JS, type definitions, and the stylesheet. We build and review components in isolation in a component workbench (e.g. Storybook or Ladle). Each component has “stories” for its different states, so design and engineering review the same thing before any app touches it. The built package goes to a private package registry (e.g. GitHub Packages, a private npm org, Artifactory, or a self-hosted Verdaccio). Each app installs it like any other dependency. The app just needs a small registry config pointing our package scope at that registry, plus a read-only access token.

*Publishing is automated but opt-in*: A CI pipeline (e.g. GitHub Actions, GitLab CI or CircleCI) watches the main branch. It publishes a new package only when the version number in the package manifest changes. Merging normal work doesn’t release anything; a release happens only when someone deliberately bumps the version. That keeps the registry clean and every release intentional.

*Day-to-day development flow*: 1) Build or update the component in the workbench, with stories for every state (default, hover, disabled, error, loading, empty, etc.). 2) Export it from the library’s public entry file so apps can import it. 3) Get it reviewed (design review in the workbench, code review in the PR) and merge it to main. 4) Bump the version with one of the helper scripts below and push the commit and tag. CI then publishes the new version. 5) In each app, update the library dependency to the new version, check the screens that use it, and ship the app through its normal deploy process. Production only changes when an app picks up the new version and deploys, so publishing a library version never changes a live site by itself. Tip: to try unpublished library changes inside an app, link it locally first (e.g. npm link, yalc, or a local file path dependency).

*When to bump which version (semantic versioning)*: PATCH (1.4.2 → 1.4.3) is for bug fixes and visual tweaks that don’t change how the component is used, like fixing padding or a color or an a11y issue. MINOR (1.4.2 → 1.5.0) is for new things that don’t break existing usage: a new component, a new optional prop, a new variant or a new design token. MAJOR (1.4.2 → 2.0.0) is for anything that could break an app: removing or renaming a component, prop or token, changing a default behavior, or requiring a newer framework version. One gotcha: while you’re still below 1.0.0, package managers treat a minor bump (0.7 → 0.8) as breaking, so apps won’t pick it up automatically. That’s fine early on, but it’s worth knowing.

*Helper scripts (the most useful part)*: We added these to the library’s package manifest so a release is one command: `“preversion”: “npm run lint”` runs the type check or lint first and blocks the release if it fails. `“postversion”: “npm run build”` rebuilds the package after the bump. `“release:patch”: “npm version patch”`, `“release:minor”: “npm version minor”` and `“release:major”: “npm version major”` each bump the version number, create the commit and tag the release (e.g. v1.4.3) in one step. The release flow is then: commit your work (the working tree must be clean), run `npm run release:patch` (or minor/major), then `git push && git push --tags`. CI takes it from there. Other package managers (yarn, pnpm) have equivalent version commands.

*A few lessons learned*: Ship the design tokens as a CSS file in the package so apps never copy colors by hand. If the apps use utility CSS (e.g. Tailwind), set up each app to scan the library’s built files for class names, or styles will silently go missing. If an app uses server-side rendering (e.g. Next.js Server Components), mark the bundle as client-side code in a post-build step so it imports cleanly. Keep peer dependencies (like React) as peers, not bundled dependencies, so apps don’t end up with two copies. Hope this helps, and happy to jump on a call with the team if useful!
